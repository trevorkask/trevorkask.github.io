Lecture 1: Introduction

Why distributed systems exist, what makes them hard, and the MapReduce model.

Why distributed systems?

  • Parallelism for high performance: lots of CPUs and lots of memory.
  • Fault tolerance: have two computers do the same thing; if one fails, cut over to the other one.
  • Naturally spread out: bank A has a computer in NYC and another in London, and they need to communicate.
  • Security: if there is code you do not trust, split the computation and isolate pieces so they communicate over a narrow path.

Challenges

  • Concurrency: a distributed system has many parts communicating concurrently, which creates weird timing problems and interleavings across computers.
  • Partial failures: networks and multiple moving pieces create unexpected failure patterns. Some pieces stop working while others continue. Sometimes the computers are working but part of the network is broken or unreliable. In a one-computer setup, it either fails or works.

Infrastructure and abstractions

  • Storage

Implementations

Performance

We can start by creating more servers to handle requests to the database. At some point, more servers will not increase performance because the database becomes the bottleneck. It is not straightforward to set up multiple databases.

Fault tolerance

  • It is not uncommon to have one computer stay up for an amazing amount of time. However, with 1000 computers, even if each computer is expected to stay up for a year, you will have about 3 computer failures a day.
  • A computer could crash or hang. A cable could get stepped on.
  • We need infrastructure that hides the failure from application users.
  • Availability: under certain kinds of failures, the system continues to operate as if there were no failure. For example, a replicated service on two computers can still serve from one. If both fail, we cannot offer the service anymore.
  • Recoverability: if something wrong happens, it can be fixed and come back up.
  • We need non-volatile storage like hard drives.
  • Replication: managing replica copies is tricky. If two servers each have a supposedly identical copy of the system's data, the key problem is that the replicas can drift out of sync. To avoid correlated faults, replicas should not be close to each other, such as in the same rack. If someone steps on a cable, both replicas might die. We therefore put replicas in different cities or countries.

Consistency

  • put(k, v) and get(k) -> v.
  • In a distributed system, there is usually more than one copy of the data. With one table of data, it is simple to reason about what these two functions mean.
  • If both servers have {k: 1, v: 20} and a put(1, 21) updates both copies, one server might crash after only one copy is updated. One replica has 20 and the other has 21. Most gets may return 21, but one day you could weirdly get 20 instead. Not very consistent.
  • Strong consistency: some version of a guarantee that get sees the most recent put.
  • Weak consistency: does not make that guarantee, and there are many flavors of it. We still like it because strong consistency is expensive. The writer, reader, or both must consult all copies and use the most recently saved value they have seen. When replicas are in different cities, this becomes slow.

MapReduce

  • Google had the problem of analyzing pages and figuring out which ones were useful. Even back then, this was several terabytes. They also had to build an index of all pages, which is intensive and takes a lot of time, similar to sorting.
  • The map function runs on each input file and outputs a list of key-value pairs. For example, when counting word occurrences, the key is the word and the value is the count.
  • The reduce function sums up the findings from each output and returns one output.
  • The whole thing is called a job and contains several map and reduce tasks.
Map(K, V)
  K is the file name and V is the file contents
  Split V into words
  For each word W:
    emit("W", 1)

Reduce(K, V)
  K is the word and V is a vector of 1s
  emit(len(V))
