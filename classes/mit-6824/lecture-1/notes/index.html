LECTURE 1: INTRODUCTION

Why distributed systems?
- Parallelism for High performance - lots of CPUs, lots of memory
- Fault tolerance - have two computers do the same thing, if one fails, cut over to the other one
- Naturally spread out - bank A has a computer in NYC and another has another one in London and they need to communicate
- Security - if there's code you don't trust, you split the computation and isolate them so they communicate over a narrow path

Challenges:
- Concurrency - Since a distribute system has many parts and the parts communicate concurrently, we have weird timing problems interleaving across the computers.
- Partial failures - Since we have a network and multiple moving pieces, we can have very unexpected failure patterns. Some pieces stop working and other pieces continue working. Or maybe the computers are working but some part of the network is broken or unreliable. In a one computer setup, it either fails or it works.

Performance:
- We can start by creating more servers to handle requests to the database. At some point, more servers won't increase the performance and the database will be the bottleneck. It's not straightforward to setup multiple databases.

Fault tolerance:
- It's not uncommon to have one computer. They stay up for an amazing amount of time. However, if you have 1000 computers, even if each computer is expected to stay up for a year, with a 1000, you'll have 3 computer failures a day.
- A computer could crash or hang. A cable could get stepped on.
- We need to have infrastructure that hides the failure from the application users
- Availability: Under certain kinds of failures, the system continues to operate as if there were no failure. For example a replicated service on two computers, you can still serve from one. If both fail, we can't offer the service any more.
- Recoverability: If something wrong happens, it can be fixed by someone and come back up.
- We need non-volatile storage like hard drives.
- Replication: management of replication copies is tricky. If we have two servers each with supposedly identical copy of the system's data, the key problem is that the two replicas will accidentally drift out of sync and will stop being replicas. To avoid faults, we cannot put replicas close to each other like in the same rack. If someone steps on the cable, both replicas die. We therefore put replicas in different cities or countries.

Consistency:
- put(k,v) and get(k) -> v
- One thing to think about is that in a distributed system, we usually have more than one copy of the data. In one table of data, it is usually simple to reason about what these two functions mean.
- If both servers have {k:1, v:20} and we have a put operation put(1, 21) updating both copies. Then one server crashes and we end up only updating one copy. One has 20 and the other has 21. It is possible that most gets end up returning 21 but one day weirdly, you end up getting 20 instead. Not very consistent.
- Strongly consistent - has some version of a guarantee that get sees the most recent put
- Weakly consistent - don't make such a guarantee and there are many flavors of this. We still like this because strongly consistent is expensive. Either the writer, the reader or both has to consult all copies and use the most recently saved value that they have seen. In a scenario where replicas are in different cities, this becomes very slow.

MapReduce:
- Google has the problem of analyzing pages and figuring out which ones are useful. Even back then, this was several terabytes. They also had to build an index of all pages, similar to sorting, this is intensive and takes a lot of time.
- The map function runs on each of the input file and outputs a list of key-value pairs. For example, counting the number of word occurrences. The key will be the word and the value is the count.
- The reduce function will sum up the findings from each output and have it as one output.
- The whole thing is called a job and contains several map and reduce tasks.
- Map(K,V)
  - K is the file name and V is the file contents
  - Split V into words
  - For each word W:
    - emit ("W", 1)
- Reduce(K, V)
  - K is the word and V is a vector of 1s.
  - emit(len(V))
